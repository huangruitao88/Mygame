# 侠影录 Wuxia Rogue

武侠风 2D 横版 Roguelite 动作游戏原型（**Godot 4.7** / GDScript 2.0）。
玩法参考《重生细胞》：移动-跳跃-冲刺的高速横版动作 + 三段连击 + 受击无敌帧，
并在第一关放了一名**守关 Boss**，击杀后掉落一把**随机词条武器**（可拾取、单槽装备）。

击杀敌人还会按概率掉落**能量球**：踩上去即自动吸取，永久提升一项基础属性
（攻击 / 生命 / 暴击率 / 暴击伤害）。能量球是独立于武器槽的成长层，
**换武器不会清掉已吃到的加成**——这是 Build 越打越强的关键。

## 运行方式

1. 需要 **Godot 4.7**（Standard 版即可，无需 .NET）。本项目已在 `Godot v4.7-stable` 上实测通过。
2. 打开 Godot → `Import`（导入）→ 选择本目录下的 `project.godot`。
3. 按 `F5` 运行。项目入口是**主界面** `scenes/title.tscn`，点「开始游戏」进入关卡。
   也可以按 `F6` 单独运行任意场景（`scenes/title.tscn`、`scenes/main.tscn` 都能独立跑起来）。

> 项目使用 `gl_compatibility` 渲染后端与 480×270 内部分辨率，窗口按 **3 倍整数**放大到 1440×810
> （非整数倍放大会发糊，详见「画面清晰度」一节）。
> 首次导入时 Godot 会自动把 `config/features` 写成 `("4.7", "GL Compatibility")`，属正常行为。

## 操作

**主界面**（水墨江湖样式：竖排标题 · 印章 · 月/山/雾/落花背景）

| 按键 | 动作 |
| --- | --- |
| `Enter` / `空格` | 确认当前菜单项（开始游戏 / 打开设置或存档弹窗） |
| `↑` / `↓` | 在菜单项之间切换 |
| `Esc` | 关闭已打开的弹窗；无弹窗时退出游戏 |

菜单三项：**开始游戏**（朱砂主按钮）、**设置**、**存档**。设置与存档目前是
样式还原的演示面板（内存态开关/滑块 + 静态存档槽位），尚未接入存档系统与音频总线。

**关卡内**

| 按键 | 动作 |
| --- | --- |
| `A` / `D` 或 `←` / `→` | 左右移动 |
| `空格` / `W` | 跳跃（空中可再跳一次，二段跳） |
| `Shift` | 冲刺（带无敌帧，冷却 0.55s） |
| `K` | 翻滚闪避（无敌 0.34s，可取消出招后摇，冷却 0.75s） |
| `L` | 举盾格挡（按住；挡下瞬间为**完美格挡**） |
| `J` | 三段连击（第 3 段伤害与范围最高） |
| `E` | 拾取地上的武器（装备槽只有一格，拾取会整体替换旧武器） |
| `R` | 重开本关 |
| `Esc` | 返回主界面 |

目标：从左侧出发，清掉沿途刀客（顺手收掉它们掉落的能量球），打倒守在关门前的
**守关 Boss「铁面刀客」**，捡起它掉落的武器，再走到最右侧的朱红关门「出关」。
**Boss 没倒下之前关门不开** —— 否则直接冲刺溜过去，Boss 就成了摆设。

## Boss 与武器掉落

- **守关 Boss**：`WuxiaBoss`（`extends WuxiaEnemy`）。复用杂兵的巡逻 / 侦测 / 接触伤害 / 受击硬直，
  另外加了 260 点血量、26×48 的受击盒、0.18 的击退倍率（抗打断），以及一段**可预判的突进斩**：
  前摇 0.45s 时头顶亮出红色箭簇（预警），随后以 300px/s 突进 0.5s，撞到墙或时间耗尽即收招。
  见面 0.8s 就会来第一下，之后每 2.8s 一次。
- **武器掉落**：Boss 死亡处生成 `WuxiaWeaponDrop`，悬停展示完整词条（带半透明底板），
  玩家进入范围出现「E 拾取」，按下后广播 `picked_up`，由 `game.gd` 交给玩家装备。
  （键名是从 `InputMap` 现取的，改键位不会让提示与实际按键脱节。）
- **词条规则**（`WuxiaWeapon`）：

  | | 说明 |
  | --- | --- |
  | 主词条 | **固定为「攻击」**（定值，直接加到每段连击上） |
  | 副词条 | 从 **攻击 / 生命 / 暴击 / 暴击伤害** 中**不放回**随机抽 1~4 条，数值同样在区间内随机 |
  | 品质 | 凡品 / 良品 / 珍品 / 神品，权重 40/34/20/6；品质决定副词条**条数**（1/2/3/4）与主词条数值 |

  也就是「随机掉落」由 **品质 × 词条种类 × 词条数值** 三层随机叠加而成。
- **装备槽只有一格**（`player.equip_weapon()`）：重复装备会**整体替换**旧武器并重算属性，词条永不叠加。
  生命上限跟着副词条重算，涨出来的部分当场补给玩家。

## 能量球与永久成长

- **掉落规则**（`game.gd`）：杂兵死亡按 `ORB_DROP_CHANCE = 0.4` 掷一次；**Boss 必掉一颗**
  （关卡高潮的成长反馈不该被一次随机数吃掉）。Boss 双掉落横向错开 28px，免得两件叠在一处看不清。
- **拾取方式**：靠近即被**磁吸**，不需要按拾取键 —— 永久成长要的是高频正反馈，不该再压一次按键。
  拾取后广播 `collected(stat, value)`。
- **两级半径**（`WuxiaEnergyOrb`，这是磁吸的关键）：

  | 半径 | 值 | 作用 |
  | --- | --- | --- |
  | 拾取圈 `PICKUP_RADIUS` | 16px | 真正的吸取判定，碰到才算到手 |
  | 磁吸圈 `MAGNET_RADIUS` | 64px | 纯激活圈，玩家一进来球就开始飞过来 |

  两个圈是两个独立 `Area2D`，**不是把一个圈放大**：放大拾取圈会变成「隔着半个身位就凭空吸走」，
  像判定作弊；两级半径的手感才是「先被吸引、再贴上」。
- **磁吸运动**：磁吸圈 `body_entered` → 记下目标并 `set_physics_process(true)`；
  逐帧按当前距离直接算速度（离得远 70px/s、贴近 340px/s，`lerpf` 插值），越近越快、收尾干脆。
  出圈 / 目标倒下 / 已被吸取时立刻 `set_physics_process(false)` ——
  **没人靠近的球一次距离计算都不做**，不是常驻轮询。
  球是纯 `Area2D` 不走物理体，所以位移直接写 `global_position`，会穿墙；
  磁吸半径只有 64px，视觉上察觉不到，换来实现足够简单。
- **玩家倒下则磁吸失效**：`_is_live_player()` 收口了拾取 / 进圈 / 逐帧追踪三处的判断。
  否则尸体会把球吸过去，而 `player.apply_bonus()` 会拒收死亡后的加成 —— 一颗球凭空蒸发。
- **数值区间**（比武器词条小一个量级，靠数量堆 Build 而不是一颗顶一把神兵）：
  攻击 +1~3 / 生命 +4~10 / 暴击 +0.5~1.5% / 暴击伤害 +2~6%；
  属性权重 34/34/18/14，攻击与生命常见、暴击系稀有。颜色每属性一色，混战里一眼能认出捡到了什么。
- **永久加成层**（`player.apply_bonus()`）：能量球给的加成记在 `_bonus_*` 上，
  与武器槽**完全独立**。属性的最终值是

  ```
  基础常量（BASE_*） + 永久加成（_bonus_*） + 武器词条
  ```

  三层在 `_recalc_stats()` 里**一次性整体重算**。这是本功能最容易踩的坑：
  若把加成增量写进结果值（`_attack_power` / `max_health`），下一次换武器整体重算时会被抹平，
  玩家的能量球收益就凭空消失了。冒烟测试专门有一条回归断言盯着这件事。
- **HUD**：左下角「能量球 · 攻击 +5 生命 +20」实时汇总已吃到的加成（没有加成时整行留空）。

## 主界面背景视频

主界面背景是一段**竖屏水墨武侠角色动画**（白衣双刀剑客，AI 生成），
以 `VideoStreamPlayer` 循环播放（`assets/video/title_bg.ogv`，480×270 / 10s / Theora）。

- **格式转换**：Godot 核心只支持 Ogg Theora，H.264/MP4 需先用 ffmpeg 转码
  （`tools` 外部依赖：`imageio-ffmpeg` 自带的静态 ffmpeg 即可）。完整一步合成 + 转码：

  ```bash
  ffmpeg -i assets/video/source/title_bg_full.mp4 -filter_complex \
    "[0:v]scale=480:852:force_original_aspect_ratio=increase,crop=480:270:0:291,gblur=sigma=18,eq=brightness=-0.12:saturation=0.9[bg]; \
     [0:v]delogo=x=218:y=502:w=94:h=62,scale=-2:270[fg]; \
     [bg][fg]overlay=x=264:y=0:shortest=1,format=yuv420p[out]" \
    -map "[out]" -an -c:v libtheora -q:v 6 assets/video/title_bg.ogv
  ```

  竖屏视频（320×568）放进 480×270 横屏视口用的是「**模糊放大垫底 + 居中偏右全身立绘**」：
  背景层取视频中段裁切并高斯模糊压暗，前景层等比缩到视口高、放在 x=264 ——
  右侧人物、左侧留白给竖排标题，是横版武侠标题画面的经典构图。
- **水印**：原视频右下角带「豆包AI生成」水印，转码时在**源坐标系**（320×568）用
  `delogo` 抹掉（框 `x=218 y=502 w=94 h=62`）。改构图参数时要同步核这个框的位置。
- **无音轨**（`-an`）：主界面背景视频循环 10s，带声会非常吵；项目也还没有音频系统。
  需要配乐时把 `-an` 换成 `-c:a libvorbis -b:a 96k` 重新转码。
- **循环**：`VideoStreamPlayer.loop = true`，另把 `finished` 信号接回 `play()` 做兜底。
- **缺失回退**：沿用「素材缺失自动回退」惯例——`ResourceLoader.exists()` 检查失败时
  程序化水墨背景（天空渐变 + 月 + 远山）照常接管，只打一条 warning。
- **布局联动**：视频人物在右侧，主界面 UI 相应左置（竖排标题 x≈64、印章缩小避让、
  副标题与题签左对齐）；视频缺失回退时这套左置布局同样是有效构图。
- `.ogv` 在 Godot 4 里**运行时直读**（无 `.import`、只有 `.uid`），`load()` 直接返回
  `VideoStreamTheora`，属正常现象。

## 场景背景（插画底图 + 视差）

关卡背景不再是代码画的渐变天空，而是一张**夜色山门庭院**插画底图
（`assets/backgrounds/courtyard_hall_night.png`，588×328），以 0.05 的系数做横向视差缓慢推移。

- **贴图怎么来的**：AI 生成 → 去人物 / 去 UI → 去水印 → 按游戏视口取景缩放。
  全流程收在 `tools/make_background.py` 里，可重跑：

  ```bash
  python tools/make_background.py <AI 原图> assets/backgrounds/courtyard_hall_night.png 588
  ```

  全尺寸清版（1920×1072）留在 `assets/backgrounds/source/`；该目录带 `.gdignore`，Godot 不导入。
- **为什么是 588 宽**：贴图比 480 的视口宽，多出来的部分是**视差滑移的留量**。
  底图以「相机横向行程的中点」为原点跟随，最大滑移 = `BG_MOTION_X(0.05) × 相机中心行程 / 2`；
  相机中心行程 = `(limit_right − limit_left) − 480` = 1790 + 140 − 480 = 1450，
  于是需要 `480 + 0.05 × 1450 ≈ 552.5px`，取整做了 588。
  改 `BG_MOTION_X` 或**改相机横向限位**都得同步核这个宽度，否则关卡两端会露出底图边缘 ——
  冒烟测试有一条断言按同一个算式现算所需宽度（写死的数字会在改限位时悄悄失效）。
- **位移为什么自己算**：底图挂在负层 `CanvasLayer`（屏幕空间），位置由 `_update_background()`
  按相机横坐标手算，而没用 `ParallaxBackground`。后者的分层锚点在它自己内部，
  而这张图的硬要求是「整段相机行程里始终盖满视口」，
  留量必须能直接从 `BG_MOTION_X` 算出来、并且对测试可见。
  注意它用的是**自己按限位夹过再算的中心**，不是相机节点的 `global_position`（理由见「关卡两端」一节）。
- **竖直方向不参与视差**：跳跃时远景纹丝不动，顺带省掉一份上下留量 ——
  底图顶边固定贴住屏幕顶边（`BG_TOP_Y = 0`）。
- **纹理过滤单独开线性**：项目默认是「最近邻」（像素风要的），但底图是按 **1:1** 渲染的插画
  （贴图尺寸 = 屏上尺寸，最清晰），视差又让它长期停在半像素上 ——
  最近邻 + 半像素位移 = 逐帧抖动，所以只给底图开 `TEXTURE_FILTER_LINEAR`。
- **贴图缺失自动回退**：底图没被导入（新克隆的仓库、CI 首次跑）时，程序化背景
  （渐变天空 + 山影/竹影剪影 + 厚雾）照常接管，关卡不会变成空白，只打一条 warning。

## 主角序列帧动画

主角身体从「多边形小人」换成了序列帧，目前两条动画，**帧率都是 9 FPS**：

| 动画 | 贴图 | 网格 / 帧数 | 出处 |
| --- | --- | --- | --- |
| `idle` 待机 | `assets/sprites/player_idle.png` | 5 列 × 4 行 / 20 帧 | 正面站姿的呼吸循环 |
| `run` 跑步 | `assets/sprites/player_run.png` | 4 列 × 3 行 / 9 帧 | 侧面跑步循环 |

切哪条只看水平速度：**有位移播 `run`，没有播 `idle`**。
攻击会把水平速度压到 0（`_physics_move()` 里 `attacking` 分支），所以出招时自然站定播待机 ——
「脚下生根地挥剑」比「一边跨步一边挥剑」更对。

- **贴图怎么来的**：两张源序列图都用 `tools/make_player_sheet.py` 一步处理：

  ```bash
  python tools/make_player_sheet.py <跑步源图> assets/sprites/player_run.png --flip-x
  python tools/make_player_sheet.py <待机源图> assets/sprites/player_idle.png --cols 5 --rows 4 --frames 20
  ```

  脚本会①按需逐格镜像；②逐格量出角色内容的包围盒，算出**帧锚点**（会直接打印出来，
  需抄进 `player.gd` 的 `ANIMS`）；③按**目标角色高度**把整张图缩放到 1:1。
  源图留在 `assets/sprites/source/`（带 `.gdignore`，不参与导入）。
- **按「目标角色高度」缩放，不是按格子边长**：两张源图的格子尺寸不同
  （跑步图 256×256、待机图 256×341，角色分别高 219 / 307px）。按格子边长缩，
  两条动画的角色就会一大一小、一切换就「变大变小」；按角色高度（48px）缩才是同一个体型。
- **为什么要预缩放**：主角在 480×270 的视口里只有约 48px 高，源图要缩到 **0.16~0.22 倍**。
  交给 GPU 实时缩，四五倍最小化 + 无 mipmap 会一路闪烁 —— 预缩放用 LANCZOS 一次做好，
  运行时 1:1 绘制，与背景底图同一套「1:1 最清晰」原则。
- **帧锚点与绘制偏移是「每条动画各自的事」**：待机格 40×53、跑步格 56×56，锚点比例也不同，
  所以 `_apply_anim()` 切动画时会同步换 `AnimatedSprite2D.offset`。
  共用一个 offset 会让角色在切换的那一帧纵向跳一下。锚点用比例而不是像素，
  换尺寸重跑脚本时不用改代码；但**镜像会改锚点的 x**，重跑脚本要同步更新。
- **朝向约定：美术一律朝 +x（右）**。翻面靠 `_visuals.scale.x = _facing`，所以序列图本身必须朝右，
  否则会「倒着跑」。跑步这张源图角色是朝左的，所以命令行带 `--flip-x`；
  待机那张是正面姿势、不需要翻。脚本会自带朝向自检（见下）。
  注意 `--flip-x` 是**逐格镜像**而非整张图镜像：整张图翻会让帧序也反过来。
- **朝向自检是启发式的，所以它会自己报可信度**：只看角色头部区域的肤色像素落在内容横向的百分之几处。
  只看头部是因为手也是肤色（待机姿势双手垂在身侧，全身一起算会得到 30%~53% 乱跳的结论）；
  另外脚踩 `--flip-x` 判断时只看**帧间是否稳定** —— 侧面姿势的比例很稳，正面姿势会来回跳，
  于是脚本对正面图只报「朝向不明显」而不误报「朝左」。
- **朝向翻转仍然归 `_visuals.scale.x`**（不用 `AnimatedSprite2D.flip_h`）：
  锚点已经对在 x=0 上，整体镜像后锚点仍在原处 —— 翻面不会让角色横向跳一下。
- **空中不做特判**：跳跃保留水平速度就继续播跑步，站着起跳则播待机；等有专门的跳跃 / 落地帧再说。
  死亡时显式 `pause()`：物理一停 `_update_visuals()` 就不再跑，不清掉的话尸体会一直原地踏步。
- **攻击时那把多边形长剑保留**：序列帧里的角色是空手的，
  而「手里多一把剑」是「正在出招」最直接的可视反馈。
- **贴图缺失仍然有兜底**：任意一张没被编辑器导入（新克隆的仓库）时整体回退成原来的多边形小人，
  只打一条 warning。主角一隐形整局就废了，这个兜底不能省 ——
  但冒烟测试会断言两条动画确实生效，回退绝不能悄悄发生。

## 画面清晰度：整数倍放大 + 全链路像素对齐

主角是位图序列帧，敌兵与地形是矢量多边形 —— 后者天生锐利，所以只要主角糊一点就特别扎眼。
"糊"不是一个开关，是四层因素叠出来的，缺一层都能看出来：

1. **放大倍率必须是整数**。视口 480×270、窗口 1440×810 是 **3 倍**；
   之前的 1280×720 是 2.667 倍 —— 一个贴图像素要摊成 2~3 个屏幕像素，
   采样点落在纹素之间，只能靠插值抹平。`scale_mode="integer"` 兜住任意窗口尺寸
   （宁可留黑边也不做非整数放大）。改窗口请只在 **960×540（2×）/ 1440×810（3×）/ 1920×1080（4×）** 里选。
2. **过滤方式用最近邻**。主角原先单独开 `TEXTURE_FILTER_LINEAR` 是为了压住半像素抖动，
   代价就是全场最糊。对齐做好之后抖动成因消失，已改回与项目一致的 `NEAREST`
   （`player.gd::PLAYER_TEXTURE_FILTER`，一个常量，看到边缘跳就改回 LINEAR 反查）。
3. **绘制位置必须是整数像素**。三处同时成立才有效，漏一处就前功尽弃：
   - 主角：`_pixel_snap_offset()` 用子节点偏移把物理量（小数）补回整像素；
     `_anim.offset` 取整（锚点是比例，直接乘出来是 -20.468 这种小数）；
     形变 `_squash_v` 收尾吸附回 1（`lerp` 渐近，永远差 0.000x 就等于长期非整数缩放）。
   - 相机：`_process()` 里 `global_position.round()`，镜头变成逐像素移动。
   - 屏震：`camera.offset` 量化成整数像素，并保证有创伤时至少 ±1px，
     否则轻击的反馈会被量化吃掉。
4. **素材的像素密度是物理上限**。序列帧按游戏内 48px 高预缩放，3 倍窗口下就是 144px 高 ——
   再怎么优化也变不出不存在的细节。想要更多细节只能提视口（连带相机限位、底图宽度、HUD 全部重算），
   目前不值得。

## 闪避与防御：翻滚 · 举盾 · 完美格挡

两个新动作，刻意**不与冲刺复用**。最容易做糊的地方就在这里：
冲刺已经带 0.19s 无敌帧了，如果翻滚只是「另一个带无敌的位移」，那它就是多余的。

| | 冲刺（`Shift`） | 翻滚（`K`） |
| --- | --- | --- |
| 速度 / 时长 | 520 px/s，0.15s | 360 px/s，0.26s |
| 无敌帧 | 0.19s | **0.34s**（长过位移） |
| 冷却 | 0.55s | 0.75s |
| 取消出招 | ✗ | **✓** |
| 定位 | 跑图位移 | 对招 / 躲判定 |

一句话分工：**冲刺是位移，翻滚是对招**。翻滚跑得近、转得慢，换来的是更长的无敌与
「出招到一半也能滚出去」的权利 —— 看到 Boss 起手突进斩时，你不用等三段连击打完。

### 翻滚（`K`）

- **无敌帧比位移长**（0.34 vs 0.26）：收招那几帧也是无敌的。
  如果无敌和位移一样长，「滚出去了还是被蹭到」，翻滚会觉得没用 —— 无敌帧该有富余。
- **可以取消出招**：`_cancel_attack_for_evade()` 会把攻击判定盒**立刻关掉**再去滚。
  判定盒留着的话，玩家看到的是「我在滚」但实际还在出招吃判定 —— 这种不一致最伤信任。
- **位移由冲量 + 摩擦自然收掉**（`EVADE_FRICTION = 900`），与攻击前冲同一套做法：
  翻出去之后停不下来，是「被扔出去」的手感，而不是「贴着地滑一段」。
  实测净位移 ≈ 61px。
- **朝哪边滚由 `_facing` 决定**，所以起手方向就是朝向 —— 想滚向背后得先转身。
- 复用冲刺那套残影（`_spawn_ghost`），冲刺与翻滚的残影视觉上没有区分，这是有意的：
  它们表达的是同一件事（高速脱离），用两套颜色会让人以为机制不同。

### 防御（`L` 按住）：三条规则

缺任何一条，这套防御都会崩：

1. **只挡正面**（`_is_frontal`）。背后的攻击照常吃满伤害 —— 否则举着盾就天下无敌，
   战斗退化成站桩。判定方向直接用 `_facing`，与 `_visuals.scale.x` 的视觉朝向一致，
   **判定与画面天然对齐**，不会出现「看起来挡住了却掉血」。
2. **前 0.18s 内挡下 = 完美格挡**（`PARRY_WINDOW`）：**零伤害 + 回 20 架势**。
   它是防御的收益来源 —— 让玩家愿意去读对手的前摇，而不是一直按着不放。
   窗口从**每次举盾**重新起算，所以「收起盾再按」是一个有意义的操作。
3. **架势会空**（`GUARD_MAX = 60`）：非完美格挡按**原始伤害**扣 `× 1.6` 点架势，
   空了就进入 `GUARD_BREAK_STUN = 0.9s` 破防硬直，期间**举不起盾**。
   这就是「一直按着 L」的代价，逼出攻防交替的节奏。

其余数值：

| 项 | 值 | 说明 |
| --- | --- | --- |
| 格挡后吃的伤害 | **30%**（`GUARD_REDUCTION = 0.7`） | 不走完全免伤 —— 完全免伤会让防御变成唯一解 |
| 举盾移速 | **45%**（77 px/s） | 压低但**不为零**：挪不动会让人不敢用 |
| 架势回复 | 26/s，延迟 0.7s | **只在放下盾时回**；举着盾不回 |
| 每点原始伤害扣 | 1.6 点架势 | 越重的攻击越容易破防 |

- **举盾时仍然能转身**。`_face_input` 只挡出招中的转身，不挡举盾 ——
  不许转身的话「背后来敌」就成了无解局面，玩家只能等死。
- **破防会强制放下盾**（`_guard_break` 期间 `_guard_held` 被每帧清掉），
  所以硬直结束不会因为键还按着就自动举起来 —— 需重新按下，这是一个明确的惩罚窗口。
- **盾是可见的多边形**（`_update_shield`），三色区分状态：
  银白 = 举盾中 / **金黄 = 完美格挡窗口内** / 暗红 = 破防。
  光看血条纹丝不动，玩家读不出「挡住了没有」；金色窗口是关键 ——
  它是唯一能让玩家「学会」完美格挡时机的反馈。
- **HUD 架势条**贴在血条正下方（薄 5px，青→橙→暗红），
  「还能挡几下、还差多少破防」必须看得见，否则玩家只会觉得盾时灵时不灵。
- 格挡、完美格挡、破防各有独立的屏幕提示（`_show_guard_hint`），
  与掉落/暴击的 toast **分开**：格挡是高频战斗信息，混在一起会被掉落提示顶掉。

### 受击判定的顺序

`take_damage()` 里顺序是有讲究的，改动时别打乱：

```
无敌帧（翻滚 / 冲刺） → 举盾 && 正面 && 不在破防硬直 → 格挡分支
                                              ↓ 否
                                          正常受击（0.65s 无敌 + 击退 + 0.8 强度反馈）
```

`take_damage()` 现在**返回 bool**（是否被挡下）。旧调用方直接忽略返回值即可，
新增返回值的目的是让攻击方能区分「打中了」与「被挡了」，以便给不同的表现。

## 打击感：顿帧 / 屏震 / 前冲 / 残影

四样都挂在既有的出招 / 冲刺钩子上，没有新节点、没有新场景：

| 效果 | 位置 | 参数 |
| --- | --- | --- |
| 攻击前冲 | `player.gd` 的 `COMBO[].lunge` | 160 / 190 / 260 px/s → 实际前移约 12 / 16 / 31px |
| 屏幕震动 | `game.gd::_update_shake()` | 写 `camera.offset`，最大 3px，按创伤值的平方衰减 |
| 顿帧 | `game.gd::_freeze()` | 上限 75ms × 强度，暂停整棵树 |
| 冲刺残影 | `player.gd::_spawn_ghost()` | 每 0.04s 落一张，淡出 0.24s |

**统一入口**：`player.gd` 只广播一个 `impact(strength: float)`（0..1）——
「这一下有多重」由出招方算（段数基线 0.35 / 0.5 / 0.75，暴击 +0.25，挨打 0.8），
「停多久、抖多大」由 `game.gd` 翻译。手感参数集中在一处，调的时候不用回去翻招式表；
这也是本项目一贯的分工：玩法节点广播信号，`game.gd` 编排表现。

- **顿帧用 `get_tree().paused`，不用 `Engine.time_scale`**：后者只缩小 delta、帧号照常推进，
  几十次顿帧会累计出可观的模拟时间偏差，把冒烟测试里「第 N 帧玩家应该到这里」那类断言全打散；
  前者连测试自己的帧计数一起停，脚本化时间线天然保持对齐。观感上也更对 ——
  相机跟随、受击压扁、toast 淡出会一起停，正是「整个世界顿一下」。
  **`create_timer()` 的 `process_always` 必须给 `true`**：暂停期间计时器不走就永远等不到 timeout，
  整棵树会被永久暂停（症状是「第一次命中就整局卡死」，很容易认）。
  另外 `_ready()` / `_exit_tree()` 里都兜底解暂停，防的是顿帧中途切场景把暂停状态留给下一个场景。
- **屏震写 `camera.offset`，不写 `global_position`**：`_process()` 那行相机 lerp 正在写位置，
  两处都写会互相打架（震动会把跟随目标顶掉一帧）。幅度取创伤值的平方 ——
  线性衰减会让每次小命中都在抖，抖多了就变成背景在晃，反而没有打击感。
  压在 3px 以内还有个原因：`offset` 叠加在相机限位之后，抖太狠会在关卡两端露出边界外的空白。
- **前冲是速度冲量，不是位移**：判定帧 `velocity.x = _facing * lunge`，之后由**攻击摩擦**
  （`_physics_move()` 里 `FRICTION × 0.55`）自然收掉，所以实际前移 ≈ `lunge² / 2200`。
  改数值要顺手重算前移距离；上界别摸到冲刺量级，否则就成了第二段冲刺。
- **残影的关键是 `top_level = true`**：不设它，残影作为主角子节点会跟着主角一起走，
  那就成了「身上叠了个重影」而不是拖尾。用当前帧的 `AtlasTexture` 当定格快照；
  容器 `Ghosts` 刻意先于 `Visuals` 加入 → 画在主角背后。

## 关卡地形：竖井与下层石室

主地面在 x 480~620 断开成一道竖井。掉下去**不致死、不掉血**：井底是实地，
两级石阶原地就能爬回主层，不需要按 R 重开。

| 可站立面 | y | 说明 |
| --- | --- | --- |
| 主地面 | 300 | 三段大石头，中间被竖井断开 |
| 石阶二级 | 300 | x 572~620，顶面与主地面同高、右边紧贴主地面 —— 走上去就是主层 |
| 石阶一级 | 345 | x 532~620 |
| 坑底 | 390 | 底层岩体的顶面 |

四条约束，全都在 `PLATFORMS` 旁边有注释、在冒烟测试里有断言：

- **每一级落差 ≤ 单跳高度的 80%**。单跳高度 = `JUMP_FORCE² / (2 × GRAVITY)` = 480²/2800 ≈ **82px**，
  所以一级取 45px（占 55%，余 37px）。**超过 82px 就等于把这个坑变回无底洞** ——
  玩家掉下去再也上不来、只能按 R，这正是这次要修掉的毛病。
- **坑底顶面必须与主地面底边齐平**（都是 390）。留了缝的话玩家会被卡在缝里，而不是站在坑底。
- **最高一级与主地面同高、且横向紧贴**，否则爬上来还得多跳一次才走得出去。
- **底层岩体（`Rect2(-80, 390, 1790, 200)`）铺满整关，不只垫在竖井底下**。
  底图是**屏幕空间**的（竖直方向刻意不参与视差），镜头往下一沉就会穿透到岩体下方 ——
  只在井底垫一小块的话，坑底会看起来像一块**悬空的孤岛**，四周能看见庭院地面。
  铺满整关之后，竖井才是「凿在岩体里的竖井」。代价是正常游玩时屏幕最下方那 ~25px
  从庭院地面变成了岩石（审美上是更实了，但与旧画面不同）。

**相机下界同步抬高**：`limit_bottom` 从 420 改成 520。相机中心受限于
`[limit_top + 135, limit_bottom - 135]`，520 - 135 = 385 > 站上坑底所需的 370，
所以下井时镜头能跟着下去、不会被夹在主层高度上把人拍出画面。
主层正常游玩时相机中心在 280，仍在旧范围内 —— 这段下界只在下井时起作用，不影响原有取景。

## 关卡两端：封边岩壁

主地面在 x −80 与 x 1710 就是世界的尽头。**以前两端敞开**：从起点往左、或走过关门继续往右
都能走出地形，然后一直往下掉（和竖井以前一样只能按 R）。现在两端各有一道岩壁：

| | 内侧面 | 顶面 | 底面 |
| --- | --- | --- | --- |
| 左端岩壁 | x = −80（与主地面左外沿齐平） | y = 120 | y = 590 |
| 右端岩壁 | x = 1710（与主地面右外沿齐平） | y = 120 | y = 590 |

- **高度是算出来的**：一次单跳 + 一次接在顶点的二段跳，能爬升 **160px**，岩壁高出地面 180px，
  留 20px 余量。这个数必须用**逐帧离散累加**算（`smoke_test.gd::_max_jump_climb`）而不是连续公式
  `v²/2g` —— 物理是「每帧先加重力、再用当前速度位移」的欧拉积分，离散步长会多爬约 4px
  （480 的单跳连续公式算 82.3，引擎里实际 86.3）。用偏小的近似值会让余量看起来比实际大。
- **底面伸到 590**（比相机下界 520 更低）：两端不留任何能钻出去的缝。
- **相机横向限位放宽到 −140 / 1790**：`Camera2D.limit_*` 夹的是**实际取景**，
  若把左边界正好压在 −80，玩家贴住岩壁时那根岩柱整根在画面外，看起来就像撞了空气墙。
  各往外放 60px，贴壁时能看到 60px 宽的岩柱。

> **一个连带的既有缺陷（本轮修掉）**：`limit_*` 只约束取景，**相机节点的 `global_position` 照样跟着玩家跑**
> （实测玩家贴住岩壁时到了 −74 / 1704，而画面早就被夹住不动了）。而 `_update_background()` 原来就是拿
> 未夹的坐标算视差 —— 于是玩家在关卡两端走动时画面停着、底图还在滑（背景在飘），
> 底图所需宽度也被高估。现在改为自己按限位夹一次再算（不用 `get_screen_center_position()`，
> 那个要等相机内部更新、会慢一帧）。

## 关卡墙体：单跳过不去、二段跳才翻得过的三道内墙

主角能爬到 **160px**（单跳 86px + 顶点接二段跳 73px），而关卡里原先只有一道 150px 的
竖壁（x=1060，还得借助旁边的石台才上得去）—— 有 160px 的攀爬力，却没什么墙可跳。
现在沿路补了三道**内墙**（`game.gd::WALLS`，与 `PLATFORMS` 分开管），全部从主地面长起：

| # | x | 顶面 y | 离地 | 过法 |
| --- | --- | --- | --- | --- |
| 1 | 880 | 240 | 60px | 单跳就过（节奏墙，也是二段跳的对照组） |
| 2 | 1150 | 180 | **120px** | 单跳 86px 够不着，**必须二段跳** |
| 3 | 1480 | 170 | **130px** | 全场最高，**必须二段跳**（余量 30px） |

- **墙 ≠ 岩壁，约束恰好相反**。两端封边岩壁的要求是「高到翻不过去」（180px > 160px），
  内墙的要求是「必须翻得过去」（≤ 160px）。内墙一旦高过攀爬上限，就是把玩家**关在墙后面**、
  只能按 R 重开 —— 那不是难度，是软锁。所以两份数据分开，测试也各断言各的。
- **高度要用「逐帧离散」的攀爬上限去卡**，不能用连续公式（86 vs 82）：理由见上一节。
  最高那道留 30px 余量，处在「压得住单跳、又不至于翻不过去」的窄带里。
- **墙顶宽 ≥ 24px**：翻上去要有落脚点。但 30px 宽的顶面在越顶时基本会被一次性掠过
  （横向 170px/s，越顶后约 20 帧在高处），想「站到墙上」得松开方向键。
- **底面一律扎到 390**（主地面底边）：墙与地面之间不留缝，免得玩家卡进缝里。
- **视觉上靠石缝区分**（`_make_wall`）：墙与平台共用同一套石色，只多画 4px 亮顶沿
  （= 可站立的顶面）与每 22px 一道的横向石缝。纯色竖条读不出「墙」，有缝才有砌石的体量感。
- **顺带改变了 Boss 战的场地**：1150 与 1480 两道墙把守关 Boss（1420）圈进一段石墙场地。
  Boss 冲不过墙，想打它就得先翻进去 —— 这正是「守关」该有的样子；打不过也能随时翻回来。
- **敌兵也翻不过墙**（它没有跳跃），墙对双方都是硬边界。敌兵是**全图追击**的
  （`enemy.gd::_find_player()` 不看距离），所以它会追到墙根停下 —— 翻墙前先看一眼墙那边有没有刀客。

## 架构约定

这些约定是后续扩展的地基，请务必保持：

- **静态类型**：所有变量、参数、返回值显式标注类型；容器使用 `Array[Node2D]` 等类型化数组。
- **信号上行、调用下行**：组件只通过信号向上汇报（`health_changed` / `died` / `combo_changed`），
  不使用 `get_parent()` 反向取父节点。敌兵的死亡只广播 `died`，掉落与计分由 `game.gd` 决定。
- **碰撞层分工**：`1=world`、`2=player`、`3=enemy`。玩家 `mask = world|enemy`、敌兵 `mask = world|player`，
  两者互为实体阻挡（敌兵不能穿过玩家，玩家也不能穿过去）；伤害判定一律走独立 `Area2D`，不依赖物理碰撞回调。
- **攻击判定是独立 Area2D**：`monitoring` 仅在判定帧开启（wind → hit → recover 三阶段状态机），
  同一次挥击对同一目标只结算一次（`_atk_hits` 去重）。
- **判定盒后沿要越过身体中线**（`ATK_BACK_MARGIN = -6`）：若判定盒只从身前起算，
  贴身的敌兵会落在判定范围之外，导致挥砍整场落空。
- **数值集中**：伤害、前摇、判定帧等都在 `COMBO` 常量里，改手感只动这一处。
- **绘制工具统一走 `Gfx`**（`scripts/gfx.gd`）：多边形与中文字体都是纯静态工具。
  新增的 Boss、武器掉落物不该为了画一块方块反过来依赖「主角」这个无关的类。
- **贴图一律按显示尺寸预缩放，运行时 1:1 绘制**：内部视口只有 480×270，背景底图与主角序列图
  都远大于它 —— 实时缩 5 倍且没有 mipmap 就是一路闪烁。两者都走 `tools/` 下的脚本做
  LANCZOS 预缩放。新增美术资源请沿用这条。
- **窗口必须是视口的整数倍，且全场像素对齐**：见下面「画面清晰度」一节。改动窗口尺寸、
  相机跟随、屏震、主角绘制偏移时，都要保证最终落在**整数像素**上，否则主角会发糊或逐帧抖动。
- **表现参数只在一个地方调**：玩法节点（`player.gd`）只上报「这一下有多重」的归一化强度，
  具体表现（顿帧多久、抖多大）集中在 `game.gd` 的打击反馈段。以后加命中特效 / 音效也接在
  `_on_impact()` 上 —— 别把表现散进各个招式里，否则调手感要满项目找。
- **测时间相关的效果用「窗口 + 极值」，别赌某一帧**：三段连击的后摇长短不一（0.12 / 0.14 / 0.28s），
  「判定帧落在哪一帧」是会变的；屏震更是由 `game.gd` 的空闲帧写 `camera.offset`，
  在物理帧里读到的是上一帧的值。冒烟测试里前冲与屏震都按窗口取极值。
- **顿帧的可观察量是计数器，不是 `paused`**：整棵树被暂停时，测试自己的 `_physics_process`
  也停了 —— 「正在暂停」这件事它根本观察不到。`game.gd` 因此保留 `hitstop_count` 供测试与调试使用。
- **给脚本加 `class_name` 之后必须重跑 `--import`**：类名没进全局类缓存时，
  引用它的脚本会整片解析失败，表现是「场景加载不出来、进程空转不退出」，
  很容易被误判成死循环或逻辑卡死。
- **美术一律朝右（+x），翻转只在运行时做一次**：翻面靠 `_visuals.scale.x = _facing`，
  所以序列图 / 立绘本身必须是朝右的，反了就会「倒着跑」。素材朝左时在
  `tools/make_player_sheet.py` 里用 `--flip-x` 逐格翻正 —— 别在代码里加
  「这张图要反过来画」的特例，那种特例每多一个，翻面逻辑就多一处要同步。
- **精灵只负责「播哪条动画、画哪一帧」**：朝向翻转、受击倾斜、无敌闪烁、压扁拉伸仍然归 `_visuals` 管，
  序列帧挂在它下面。别把这些状态搬进 `AnimatedSprite2D` —— 主角已有 idle / run 两条序列，
  以后还会有攻击 / 跳跃，这些状态是跨序列共用的。
- **动画的尺寸参数挂在动画配置上**：`player.gd` 的 `ANIMS` 里每条动画自带
  「贴图 / 网格 / 帧数 / 帧率 / 帧锚点」—— 不同序列图的格子尺寸本来就不一样（40×53 vs 56×56），
  写成全局常量迟早会串味。切动画时 `_apply_anim()` 会同步换 `offset`，
  这是「两条序列图锚点不同」的必然结果，不是多余的一步。
- **不要拿 `AnimatedSprite2D.animation` 当「当前已应用的动画」**：给精灵赋 `sprite_frames` 时，
  引擎会自己把 `animation` 选成第一条 —— 拿它做「同名就跳过」的判据，首次调用会被挡掉，
  结果既不 `play()` 也没设 `offset`（角色顶着零偏移错位浮在半空）。
  `player.gd` 因此自己记一份 `_anim_current`。
- **背景的两条分支只在 `_build_background()` 里分岔一次**：底图路径与程序化路径各自成函数
  （`_build_image_background` / `_build_procedural_background`），雾层 `_build_haze(alpha)` 两边共用。
  别把「有没有底图」的判断散到别处 —— 否则以后新增背景元素（雨、萤火）会漏掉一条分支。
- **底图的横向留量是算出来的，不是试出来的**：`BG_MOTION_X` 与贴图宽度是一对
  必须同步的常量（见「场景背景」）。改一个不改另一个，关卡两端就会露出底图外的空白。
- **生成顺序不能反**：`enemy._ready()` 会记录巡逻原点 `_origin_x`，所以必须在 `add_child()` **之前**
  摆好坐标；写在 `add_child()` 之后，原点会停在 0，敌兵会一路走到平台边缘发呆。
- **继承要有边界**：Boss 继承敌兵，是因为它要的正是「同一套巡逻 / 侦测 / 受击机制，换一套数值」。
  一旦 Boss 需要独立的行为树或阶段切换，就该拆成组件挂上去，而不是继续往下叠继承。
- **装备槽只有一格**：`player.equip_weapon()` 是「基础值 + 当前武器」**全量重算**，不做增量加减 ——
  只有一格槽位时，全量重算最不容易在替换武器时漏掉某条词条。
- **永久成长要独立成层**：能量球这类「不会被替换掉的加成」必须自己存一份（`_bonus_*`），
  再参与 `_recalc_stats()` 的整体重算。任何「直接改结果值」的写法都会在下次换武器时被重算抹掉。
- **属性枚举只有一套**：能量球复用 `WuxiaWeapon.Stat` 与 `WuxiaWeapon.format_stat()`，
  不另立平行枚举 —— 否则 `_recalc_stats()` 里会长出两套分支，掉落物也各写一套格式化。
- **磁吸靠信号激活，不靠轮询**：`_physics_process` 默认关闭，进磁吸圈才 `set_physics_process(true)`，
  出圈 / 目标倒下 / 已被吸取就关掉。需要逐帧行为不等于需要逐帧检测 ——
  让 `Area2D` 替你做距离判断，比每帧遍历玩家列表便宜得多。
- **一个查询收口一处规则**：`_is_live_player()` 同时服务于拾取、进圈、逐帧追踪三处，
  避免同一条「活着的玩家才算目标」的规则被抄成三份、改漏一份。
- **物理回调里不能直接改物理状态，也不能直接给新节点注册碰撞体**：`Area2D.body_entered` 是物理查询回调，
  在回调内直接写 `monitoring = false` 会被引擎拒绝
  （`Can't change this state while flushing queries`），掉落物就永远吃不掉了 —— 必须 `set_deferred()`。
  同理，**掉落物本身几乎都是在攻击判定回调里生成的**，它若在 `_ready()` 里直接建拾取圈，
  每次击杀都会刷一条同样的 ERROR。两个掉落物都把物理侧收进 `_setup_physics()`，用 `call_deferred`
  推到 flush 之后再注册（延迟一帧对玩法无感：球刚落地那帧玩家不可能已经站在上面）。
  这条约束有专门的冒烟测试用例盯着（见「测试与验证」）。
- **掉落物不碰装备逻辑**：`WuxiaWeaponDrop` 只广播 `picked_up`，装备时机与「只能装一件」的规则
  由 `game.gd` / `player.gd` 决定。`WuxiaEnergyOrb` 同理，只广播 `collected`。
- **掉落容器分开挂**：武器掉落挂 `Pickups`、能量球挂 `Orbs`。两者拾取方式与生命周期都不同，
  分开还能让冒烟测试各自断言子节点数，互不干扰。
- **冲刺与翻滚是两件事，别合并**：冲刺 520px/s / 无敌 0.19s / 冷却 0.55s / 不能取消出招；
  翻滚 360px/s / 无敌 0.34s / 冷却 0.75s / **能取消出招**。
  它们共用的只有「冲量 + 摩擦」这套位移做法与残影表现。
  一旦让翻滚变成「更快的冲刺」，或者给冲刺加上取消出招，两个键就会退化成同一个，
  玩家的选择也随之消失。冒烟测试里有同条件对照断言（`_check_dash_reference`）盯着这条。
- **「什么算举盾」只写在一处**（`_guard_active()`）：按着键 + 不在破防硬直 + 不在翻滚/冲刺 + 活着。
  这个查询同时服务于「受击要不要走格挡分支」「移速要不要打折」两处，
  抄成两份的话，改一处漏一处就会出现「不能动但能挡」这类自相矛盾的状态。
- **举盾不算「出招中」**：`_physics_move(delta, busy)` 的 `busy` 只表示出招（脚下生根），
  举盾走的是「降速移动」那条路。把举盾塞进 `busy` 会让 `GUARD_MOVE_SCALE` 变成死代码 ——
  这个错误真的发生过，现在有断言（`_check_guard_move`）同时卡上下界：
  峰值必须 > 0（能缓步挪）且 < 正常跑速（防御有代价）。
- **「什么算正面」复用 `_facing`**：`_is_frontal()` 与 `_visuals.scale.x = _facing` 用同一个朝向值，
  判定与画面天然对齐。别另外维护一套「攻击来自哪边」的坐标判断 —— 两套一定会不同步。
- **受击判定链的顺序**（`take_damage`）：无敌帧 → 正面格挡 → 正常受击。
  格挡分支必须在无敌帧**之后**：翻滚/冲刺的无敌期内什么都不该结算，
  否则「滚开了还被扣架势」会让无敌帧失去意义。
- **`take_damage()` 返回 bool 表示是否被挡下**。这是为攻击方区分「命中 / 被挡」留的口子，
  现有调用方忽略它即可，不是破坏性改动。
- **举盾的按住状态每帧与输入对齐**（`_sync_guard_hold` 里读 `Input.is_action_pressed`），
  不只依赖 `_unhandled_input` 的按键事件：后者收不到「松开」，
  一旦松开事件被别的节点吃掉、或者中途切场景，盾就会永远举着。
- **一次性结果用独立字段记录，不要靠反推**：格挡结果（`_last_guard_result`）单独存一份，
  而不是让测试去对比「血量变没变 / 架势涨没涨」来反推。
  完美格挡与普通格挡的区别（零伤 + 回架势）恰好让数值断言可以懒省事，
  但那两件事在实现改动后很容易碰巧相等 —— 有一条断言直接读这个字段（`_check_perfect_parry`）。

## 已知限制 / 后续路线

当前是 **Phase 1：可玩切片** + **Phase 4 的第一块内容（Boss 与武器掉落）**。以下均未实现：

- **Phase 2 · 关卡与手感**：~~受击顿帧（hitstop）~~、~~残影~~、~~屏幕震动~~、~~攻击位移~~、
  ~~翻滚闪避~~、~~举盾防御（含完美格挡与架势）~~ 已完成；
  还剩**单向平台**与**蹬墙跳**。
  内墙（`WALLS`）已经把竖面铺开，蹬墙跳接上它们就能做出「顺着墙面往上爬」的路线 ——
  目前墙只能靠二段跳逐道翻越，还不能贴着墙面上行。
- **防御系统的后续可扩展点**：目前格挡只认「正面 / 背后」这条一维判定，
  没有区分高低位攻击；完美格挡只有「零伤 + 回架势」的即时收益，还没有弹反硬直
  （挡住 Boss 的突进斩后它该有一个更大的硬直窗口 —— 那需要 Boss 侧配合，
  给 `take_damage` 的返回值加一条「被完美格挡」的语义）。
- **Phase 3 · Roguelite 循环**：房间随机拼接、关间三选一强化（遗物）、金币与商店、复活/死亡结算。
  能量球已经是「局内永久成长」的第一块：它的加成层（`_bonus_*`）天然就是关间继承与遗物的落点 ——
  接 Roguelite 循环时只要把这一层从 `WuxiaPlayer` 提到一局持久的地方（如后续的 `RunManager`），
  而不是重新设计一套成长系统。
- **Phase 4 · 内容与表现**：多种敌兵、Boss 第二阶段、武器差异化（剑/刀/拳的招式不同，
  目前所有武器共用同一套三段连击，只在数值上不同）、技能冷却、音效与粒子；
  武器可考虑扩成「主词条随机属性 + 强化等级 + 词条洗练」。
  表现层目前是**混搭**：主角是插画序列帧，敌兵与地形还是多边形 —— 主角也还只有 idle / run
  两条序列，缺跳跃 / 下落 / 攻击 / 受击序列（现在跳跃沿用跑步、空中站着起跳则播待机）。
  另外待机序列是**正面站姿**、跑步序列是**侧面**，静止与移动之间的转身感略有跳跃 ——
  等有「侧面待机」或过渡帧再补。
- **Phase 5 · 工程化**：`EventBus` 自动加载做跨场景通信、`Resource`（`EnemyData` / `RelicData`）驱动配置、
  对象池管理弹幕与特效；武器若要做成可保存的掉落，还需要把 `WuxiaWeapon` 落成 `.tres` 资产。

## 注意

- `.tscn` 文件中不要写注释，Godot 的解析器不支持。
- 不要手写 `uid`，交给编辑器自动生成。
- 新增场景/资源优先在 Godot 编辑器里创建（右键 → 新建场景/新建资源），比手写文件更安全。
